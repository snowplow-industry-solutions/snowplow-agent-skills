# Server-Side Tracker Gotchas

The failure modes the Node, Python and Java tracker docs undercover, plus the checklist to run any other Snowplow server tracker through. Every entry names its source so it can be re-verified when a tracker releases. Mechanics (constructors, setter names, emitter options, install commands) are deliberately absent — fetch them live via `fetch-snowplow-docs` from the pages listed at the bottom.

Verified 2026-08-26 against `@snowplow/node-tracker` 4.8.0, `snowplow-tracker` (Python) 1.0.3 and `snowplow-java-tracker` 2.1.0 and the docs pages of that date. Node emitter and identity behaviour was read from the tracker source on `master` (`trackers/node-tracker/src/tracker.ts`, `libraries/tracker-core/src/core.ts`, `libraries/tracker-core/src/emitter/index.ts`, `libraries/tracker-core/src/emitter/event_store.ts` in `snowplow/snowplow-javascript-tracker`).

Docs base for every source below: `https://docs.snowplow.io/docs/sources/`.

## Cross-tracker

**Buffered emitters lose events on exit.** Events sit in the emitter until the batch fills — Node `bufferSize` 10 (POST), Python `batch_size` 10, Java `batchSize` 50 — and none of the three flushes on a timer by default: Node's emitter has no interval at all (only `flush()`), Python's `set_flush_timer()` is opt-in, Java waits for `flushBuffer()`. A script, cron job, serverless handler, or a server that exits on SIGTERM without flushing drops whatever is buffered. Flush before the process returns — `await tracker.flush()` in Node, `tracker.flush()` in Python, `tracker.close()` in Java — and give low-volume services that never reach the batch size a scheduled or per-request flush. *Source: node-js-tracker/initialization (`bufferSize`); tracker-core `emitter/index.ts` (no timer); python-tracker/emitters (`batch_size`, `set_flush_timer`); java-tracker/configuring-how-events-are-sent (`batchSize`, `flushBuffer`).*

**Identity is per request, not per tracker.** One tracker instance serves every request in the process, so a user ID, IP or user agent set on the tracker applies to every event from every request until something overwrites it. Python and Java expose a per-event Subject for exactly this — build one from the request and attach it to the event. Node has no per-event Subject: `setUserId`/`setIpAddress`/`setUseragent` write into a shared payload map and `setDomainUserId`/`setNetworkUserId`/`setSessionId` into shared tracker variables; `track()` copies them synchronously at the moment it is called. The Node rule: set every identity field and call `track()` in the same synchronous block — no `await` between them — and never rely on a value a previous request set. Whether an interleaving actually bites depends on how the application is built, which is why this is a rule to follow, not a bug to report. *Source: python-tracker/subject and python-tracker/tracking-specific-events#event-subject; java-tracker/tracking-specific-client-side-properties#adding-subject-properties-to-events; Node from `trackers/node-tracker/src/tracker.ts` and `libraries/tracker-core/src/core.ts`.*

**No cookies, no identity.** A server has no `_sp_id` or `sp` cookie of its own, so `domain_userid` and `domain_sessionid` are empty and `network_userid` is a fresh value per request — the collector issues a new cookie to each server call. Supply all three from the incoming request as SKILL.md step 4S describes; nothing downstream (Unified Digital, session models) joins server events to the client's session otherwise. Java's `OkHttpClientWithCookieJarAdapter` persists the collector cookie in memory only — it makes every event from one server *share* a `network_userid`, it does not make it the user's. *Source: python-tracker/subject; java-tracker/tracking-specific-client-side-properties (and #persisting-cookies-using-a-cookiejar); node-js-tracker/configuration.*

**The server's IP, user agent and timezone leak into enrichments.** Defaults are the server's own address and the HTTP client's UA (Java: `okhttp/4.x`), so the IP-lookup, YAUAA and UA-parser enrichments describe the data centre. Set both from the request (`X-Forwarded-For` / `X-Real-IP` behind a proxy, the `User-Agent` header). Java also fills `os_timezone` with the server's zone whenever a Subject is attached; an empty-string IP in Java suppresses IP tracking entirely. *Source: java-tracker/tracking-specific-client-side-properties#overriding-autogenerated-event-properties; python-tracker/subject#set_ip_address; node-js-tracker/configuration.*

**Client errors are not retried.** A collector response of 400, 401, 403, 410 or 422 deletes the payload in all three trackers; other failures retry with backoff. A wrong collector URL, a collector behind auth, or a payload the collector rejects is silent loss, not a crash — the process keeps running with nothing arriving. Prove the collector URL with one event in Micro before wiring the rest (Node and Java want the protocol in the URL; Python takes a bare host with protocol and port as separate arguments). *Source: python-tracker/emitters#what-happens-if-an-event-fails-to-send; java-tracker/configuring-how-events-are-sent; tracker-core `emitter/index.ts` `dontRetryStatusCodes`.*

**Buffers are bounded and drop silently.** During a collector outage Python and Java hold 10,000 events in memory and drop new ones when full (Java `track()` returns `null`; the only signal is the `FailureType.TRACKER_STORAGE_FULL` emitter callback). Node's store holds 1,000 and drops the oldest. Node also skips any single event larger than `maxPostBytes` (40,000 bytes) with a log warning only — an oversized entity array never sends. *Source: python-tracker/emitters#configuring-how-events-are-buffered; java-tracker/configuring-how-events-are-sent (and #using-the-emitter-callback); tracker-core `emitter/event_store.ts` `maxSize`, `emitter/index.ts` `maxPostBytes`.*

**Custom timestamps are milliseconds and mean `true_timestamp`.** In Python and Java the optional timestamp argument is milliseconds since epoch and sets `true_timestamp`; the tracker still stamps `dvce_created_tstamp` with now. Backfills and replays that pass seconds land in 1970; ones that expect to set `dvce_created_tstamp` get a `derived_tstamp` they did not intend. Node's tracking-events page does not say which field its timestamp argument sets — read the fetched page for the current release before relying on it. *Source: python-tracker/tracking-specific-events#timestamp-argument; java-tracker/tracking-events#adding-custom-timestamps-to-events; node-js-tracker/tracking-events#timestamps.*

**Entities are always an array, and the tracker validates nothing.** One entity still goes in a list. No server tracker checks a payload against its schema — mismatches surface as failed events at enrichment, in Micro's `/bad`, which `debug-failed-events` reads. Python's contracts raise `ValueError` on argument types only, not schema shape. *Source: node-js-tracker/tracking-events; python-tracker/tracking-specific-events and python-tracker/contracts; java-tracker/custom-tracking-using-schemas.*

## Node

`@snowplow/node-tracker` 4.x — Actively Maintained; Snowtype-supported.

**v4 needs Node 18+ and a v4 snippet.** v4 sends with native `fetch`; `got`, `gotEmitter` and `tracker()` are gone, so any v3 example (including ones the model remembers) fails at import. The entry point is `newTracker(trackerConfig, emitterConfig)`. *Source: node-js-tracker/migration-guides/v3-to-v4-migration-guide; node-js-tracker/initialization.*

**`platform` defaults to `srv`.** Nothing to set unless the events should look like something else. *Source: node-js-tracker/configuration#set-the-platform-id-withsetplatform.*

**Identity setters are tracker-global.** See "Identity is per request" above — one synchronous block per request.

**`flush()` returns a Promise.** Await it before the process exits (shutdown hook, end of a job, end of a serverless handler); calling it without awaiting flushes nothing in time. *Source: node-js-tracker/initialization; tracker-core `emitter/index.ts`.*

## Python

`snowplow-tracker` 1.x — badged **Early Release**; **not supported by Snowtype**. Tell the user both before installing. *Source: tracker-maintenance-classification; event-studio/implement-tracking/configuration-reference (supported tracker table).*

**The default `Emitter` is synchronous.** It sends on the request thread and blocks the handler until the collector answers; `Snowplow.create_tracker()` gives you that one. Use `AsyncEmitter` in any web framework. *Source: python-tracker/emitters#the-asyncemitter-class; python-tracker/intialization.*

**Default platform is `pc`, not `srv`.** Set `srv` explicitly so backends are consistent across languages and the events are not classed as desktop. *Source: python-tracker/subject#set_platform.*

**`flush()` blocks and can deadlock.** It is synchronous by default; called inside an `AsyncEmitter` `on_success`/`on_failure` callback it deadlocks. `flush(False)` is the asynchronous form. *Source: python-tracker/emitters#manual-flushing.*

**Re-tracking from `on_failure` duplicates events.** Retry is built into the emitter; the callback is for observability, not resending. *Source: python-tracker/emitters#on_failure; python-tracker/upgrading.*

**`app_id` defaults to `None`.** Pass it, or every event arrives with no `app_id`. *Source: python-tracker/intialization.*

## Java

`snowplow-java-tracker` 2.x — Maintained; Snowtype-supported.

**The JVM will not exit until `tracker.close()`.** `BatchEmitter` threads are non-daemon. Call `close()` on shutdown; it cannot be restarted, and events tracked after it are stranded in the buffer. *Source: java-tracker/installation-and-set-up#stopping-the-tracker.*

**The core artifact has no HTTP client.** Gradle/Maven must add the OkHttp or Apache HTTP capability dependency; the core alone compiles and then fails to send. *Source: java-tracker/installation-and-set-up#install-using-gradle.*

**Some configuration is silently ignored.** `bufferCapacity` is discarded when an `eventStore` is supplied; `collectorUrl` and `cookieJar` are ignored when a custom `HttpClientAdapter` is supplied. *Source: java-tracker/configuring-how-events-are-sent.*

**`threadCount` defaults to 50.** Size it for the host rather than accepting the default on a small container. *Source: java-tracker/configuring-how-events-are-sent#configuring-the-java-tracker-threads.*

**Legacy `EcommerceTransaction` emits one event per item and is slated for deprecation.** Model purchases as a self-describing event with entities instead. *Source: java-tracker/tracking-events (EcommerceTransaction section).*

## Any other server tracker

If the user asks for a tracker other than Node, Python or Java (Go, .NET, Ruby, PHP, Scala, Rust, Lua, Unity, C++), refer to the Snowplow docs site via `fetch-snowplow-docs` and, where the docs are thin, the tracker's source code — every Snowplow tracker is open source on GitHub under the `snowplow` organisation — to understand that tracker's specific behaviour. Check the tracker's maintenance badge (Actively Maintained / Maintained / Early Release / Unsupported; definitions at `tracker-maintenance-classification`) and tell the user what it means before installing.

Run the tracker through the cross-tracker section above as a checklist, verifying each against its docs or source: batch size and whether anything flushes on a timer; how to flush or close before exit; which status codes are not retried; buffer capacity and drop behaviour; whether identity is per event or per tracker; the default `platform` value.

The old Tracking CLI is deprecated; `snowplow-cli send-events` replaces it for sending test events from a shell.
